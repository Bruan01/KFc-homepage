本轮已完成第一至第三阶段的核心工作：作者等级与 GIF 上传修复、去重浏览热榜、列表与详情批量序列化、回复分页、前端失败重试与请求竞态处理、帖子/回复编辑删除、举报与后台处置、操作审计、加热幂等与退款保护、单帖点赞成就统计，以及后台论坛治理页面。第四阶段的草稿、收藏、引用和提及仍属于后续增强项。

## 一、总体判断

论坛已具备分类、发帖、回复、点赞、图片上传、Markdown 展示、搜索、热榜、积分加热、分享入口和部分通知能力。下一阶段应先修复数据显示与交互正确性，再补齐内容管理，最后扩展社区功能。

最值得优先处理的是：

1. 作者等级查询错误，导致等级回退为 0。
2. GIF 上传读取位置错误，可能保存空文件或损坏文件。
3. 热度计算仍使用可重复累加的总浏览量，去重浏览没有起到预期作用。
4. 搜索和分页请求缺少可靠的状态协调，失败还会显示成“没有内容”。
5. 列表存在逐帖查询，详情一次返回全部回复，内容增长后请求成本会持续上升。
6. 发帖后的编辑、删除、举报与后台处置流程尚不完整。

## 三、功能改进清单

### F1 · P0：修复作者等级显示

**状态：已完成。**

`apps/forum/views.py` 的 `_author_payload` 使用不存在的 `PointAccount.username` 字段，异常被转换为等级 0，因此真实等级无法正常展示。

已按用户关联读取积分账户，并在列表与详情中批量获取作者资料；缺少账户按 0 级展示，查询异常写入日志。

**验收：**具有不同真实等级的用户，在列表和回复中展示正确等级；账户缺失有明确默认规则；测试能捕获无效字段查询。

### F2 · P0：修复 GIF 上传

**状态：已完成。**

`apps/forum/views.py` 的 `upload_image` 在 `image.load()` 后直接调用 `upload.read()`，未回到流开头。GIF 分支可能保存空内容或不完整内容。

保存原始 GIF 前会重新定位输入流，保留动画帧，并对空内容与解码失败返回明确错误。

**验收：**上传后文件可打开，动画仍能播放，数据库记录的文件大小与实际文件一致。

### F3 · P1：明确浏览与热榜规则

**状态：已完成。**

`apps/forum/services.py` 中热度重算使用 `max(topic.views, topic.dedup_views)`。总浏览量通常大于去重浏览量，因此重复访问仍会影响热度。积分加热也应采用相同的基础热度口径。

展示仍保留总访问量，热榜和加热统一使用每日去重浏览量；去重浏览记录按访客与日期约束，热榜任务改为批量写入。

**验收：**同一访客同一天重复访问不会继续增加浏览热度分；新访客、跨日访问、加热到期均符合规则；重算与购买加热使用一致公式。

### F4 · P1：让搜索、切换分类和翻页可靠

**状态：已完成代码实现，待服务启动后执行浏览器 E2E。**

`static/forum.js` 中 `fetchTopics` 将失败转换为空列表；`loadTopics` 加载期间直接拒绝新请求，旧响应又可能覆盖新筛选状态；加载更多在请求成功前递增页码，且缺少充分的重复点击保护。

已实现：

- 分开处理首次加载、真正空列表、失败和重试状态。
- 使用请求序号或取消机制，只有最新筛选请求能更新界面。
- 加载更多成功后再更新页码，失败保留原列表与页码。
- 加载中禁用重复操作，并按帖子 ID 去重。
- 详情请求也校验当前选中的帖子，避免快速点击后显示旧请求结果。

**验收：**慢网连续切换分类，最终结果与当前分类一致；断网显示重试；重复点击不跳页、不重复追加、不弹出错误帖子。

### F5 · P1：补齐帖子生命周期与管理闭环

**状态：已完成。**

模型已有关闭、删除、置顶、精选字段，`apps/forum/admin.py` 也有管理配置，但当前项目未接入 Django Admin 路由，不能将这些配置视为已经可用的后台管理界面。

已补充作者/管理员编辑与软删除、回复管理、举报幂等、lv2 管理员处置、`ForumModerationAction` 审计记录，以及后台 `/admin/forum` 页面。话题下线会按剩余时长退还未结束加热，退款流水使用幂等键并带行锁保护。

**验收：**作者只能管理自己的内容；管理员操作可追溯；删除后列表与详情一致；退款最多执行一次；关闭帖子后不可继续回复。

### F6 · P1：加强积分加热的一致性

**状态：已完成代码实现，待部署配置下并发压测。**

`purchase_boost` 在事务外检查有效加热数量，扣费业务键包含当前时间。相同操作重试会得到不同键，不能实现请求幂等；并发请求也可能同时通过数量检查。SQLite 的锁行为还需要在实际部署配置下测试。

购买操作现在接受稳定幂等标识，在锁定话题的事务内校验数量、扣费并创建加热；前端扣费前展示价格、期限和热度效果，失败时保留重试状态。

**验收：**同一操作重复提交只扣一次积分、创建一次加热；并发请求不会超限；中途失败不会出现扣费成功但加热丢失。

### F7 · P1：避免互动成功但奖励或成就悄悄失败

**状态：已完成核心修复。**

论坛发帖、回复和点赞会触发积分、通知或成就计算，部分异常被忽略。`apps/gamification/services.py` 中名为 `max_topic_likes` 的聚合实际累计了多篇帖子的点赞数，并非单篇最高值，会影响依赖该统计的成就。

`max_topic_likes` 已改为按单帖聚合后取最大值；帖子、回复和点赞的奖励仍使用既有幂等流水，作者等级查询和去重浏览异常会记录日志。

**验收：**多篇帖子的点赞总和不会误触发单篇点赞成就；模拟通知失败时主操作结果明确；奖励重试不重复发放。

### F8 · P2：补齐日常使用体验

以下属于增强建议，需结合用户反馈决定范围：

| 建议 | 用户价值 | 建议边界 |
| --- | --- | --- |
| 本地草稿、离开提醒、发布防重复 | 避免长文丢失 | 先做当前用户的本地草稿，不必立即增加跨端同步 |
| 回复引用、提及与通知跳转 | 长讨论更容易跟进 | 优先浅层引用，避免无限嵌套 |
| 收藏、我的帖子、我的回复 | 便于回访 | 复用现有用户入口 |
| 明确“最新发布”和“最近回复” | 排序符合用户预期 | 当前回复更新 `updated_at`，默认列表仍按 `created_at` 排序 |
| 搜索保留条件、返回保留滚动位置 | 减少重复操作 | 与请求状态修复一起设计 |

## 四、性能改进清单

### P1：消除列表与回复序列化中的逐条查询（已完成）

`apps/forum/views.py` 已批量统计部分点赞、回复和链接，这是可以继续沿用的基础；但仍有重复工作：

- `_author_payload` 逐条查询作者和积分账户。
- 列表已调用 `_links_for_topics`，`_topic_payload` 仍再次逐帖查询链接，之后结果又被覆盖。
- `_images_payload` 逐帖查询图片。
- `_showcase_map` 预加载了展示项，却没有预加载后续访问的 `user`。
- 详情已计算 `liked_reply_ids`，序列化时仍逐回复查询是否点赞。

**实现：**构建当前页所需的作者、账户、图片、链接和互动映射，序列化函数只组装数据。列表 1/20/50 条的测量为 7/8/8 次 SQL。

**验收目标：**在固定数据结构下，返回 1、20、50 条帖子时查询数量不再随条数线性增加；匿名和登录用户分别记录基线，使用查询数量回归测试。具体绝对次数以重构后的必要查询为准。

### P1：回复分页与列表精简（已完成）

详情当前一次加载全部非删除回复；列表同时返回全文和摘要。

**实现：**详情首屏默认 30 条、上限 50 条，使用稳定排序和“加载更多”；列表不再携带全文，只返回卡片摘要；详情失败不再回退为列表数据，而是显示错误提示并保留重试入口。

**验收目标：**含 1,000 条回复的帖子仍只返回规定页大小，例如 30 条；顺序稳定，没有重复或遗漏；列表长文不会按正文长度持续膨胀响应。

### P1：降低热度任务的写入成本（已完成基础优化）

`refresh_hot_scores` 当前加载全部公开帖子并逐条更新。点赞、回复和加热已批量聚合，但写入仍随帖子数增长；SQLite 下这会增加写锁压力，实际影响需测量。

**实现：**热度计算跳过未变化值并通过 `bulk_update` 批量写入；仍需在部署环境增加任务耗时、失败和重叠运行指标。

**验收：**记录处理条数、更新条数、耗时、失败数及最后成功时间；任务可重复执行；部署触发与周期任务不会互相重叠。

### P2：按实际规模优化搜索和翻页（部分完成）

当前搜索对标题、正文、标签和作者使用 `icontains`；分页使用总数统计和偏移量；加热筛选先将全部有效帖子 ID 装入 Python 集合。

**实现与建议：**加热筛选已改为数据库 `Exists` 子查询，列表排序已增加唯一 ID 作为同值时的稳定次序。仍应通过查询计划和更大测试集确认搜索瓶颈；深分页出现问题后再引入游标分页，中文搜索质量和性能不足时再评估全文检索或独立搜索服务。

不建议仅凭目前 13 条帖子就引入 Redis、独立搜索服务或更换数据库。它们会增加部署、备份和故障排查成本，应由实际指标驱动。

### P2：图片与浏览记录的生命周期

图片通过 Django 接口读取，已有缓存时长，但可进一步评估条件请求、缩略图和静态资源分发。当前未发现未引用图片清理、用户上传配额和浏览日志保留策略。

**建议：**先补文件完整性、存储量统计和孤立文件清理，再按流量引入静态资源服务或对象存储；原图与缩略图职责分开。为浏览去重日志设置与统计规则兼容的保留周期。图片接口可按 ID 访问，应明确未发布图片和已删除帖子的图片是否允许公开读取。

**验收：**清理任务不会删除仍被帖子引用的文件；历史统计不因清理改变；重复图片请求可利用缓存；存储容量和增长速度可观测。

### P1：缓存边界和错误可观测性（缓存边界已修复）

此前详情将 `json_ok` 的内容重新包装为 `HttpResponse`，存在丢失 `private, no-store` 的风险；现已改为直接返回统一 JSON 响应。生产代理的缓存行为仍未实测。

详情现在直接返回带 `private, no-store` 的统一 JSON 响应，避免个人点赞状态被代理缓存；仍建议增加请求耗时、错误率、SQL 数量、数据库锁错误、热榜任务状态和奖励失败记录，避免仅依靠用户反馈发现后台流程失效。

## 六、后续验证方案

1. **单元与集成测试：**覆盖等级、GIF、去重热度、单帖成就统计、权限、退款、幂等和查询数量。沿用现有 Django 测试框架。
2. **浏览器测试：**登录后发帖、回复、点赞、搜索、切换分类、加载更多；模拟慢网、断网、重复点击；检查移动端布局、控制台错误及失败请求。由助手执行，服务按项目约定由用户启动。

4. **上线核对：**验证部署版本、数据库迁移、图片存储持久化、热度任务触发方式和最后成功时间。仅有脚本文件不等于部署平台确实执行。
