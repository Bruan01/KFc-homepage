# 显影多服务池、加权轮询与自动熔断设计

- 日期：2026-08-10
- 状态：用户已批准，待用户审阅本文档后进入实施计划
- 范围：`/admin/imaging` 显影服务配置、任务路由、故障切换、健康状态与可追溯记录

## 1. 目标

将现有单个 CPA 显影配置升级为可管理的多个显影服务，并使显影任务能够：

1. 同时配置任意数量的服务；
2. 在已启用且可用的服务之间按平滑加权轮询分配；
3. 当前服务失败时，在同一任务内立即尝试下一可用服务；
4. 单服务连续失败 3 次后自动熔断 5 分钟；
5. 熔断到期后通过一次真实任务请求进行恢复探测；
6. 在后台安全查看配置与健康数据，而不泄露 API Key 明文；
7. 让每次生成使用及尝试过的服务可审计、可追溯；
8. 保持现有任务状态、积分扣费/退款、用户隔离与旧单服务配置兼容。

## 2. 方案

采用数据库化服务池：每个服务独立持久化 URL、密钥、模型、超时、权重、优先级、开关及健康状态。生成代码从服务池中选择候选服务，逐个调用并记录尝试结果。

不使用进程内轮询指针作为唯一状态。平滑加权轮询所需的调度状态持久化在数据库并在选择时加锁，避免多线程/多进程部署下重复或失真的分配。

## 3. 数据模型

### `ImagingProvider`

服务配置和调度/健康状态。

- `name`：后台显示名，唯一；
- `enabled`：是否参与调度；
- `base_url`：规范化的 HTTP/HTTPS API 根地址；
- `api_key`：密钥，管理接口只返回“是否已配置”和掩码；
- `model`：该服务的生图模型；
- `timeout_seconds`：该服务请求超时；
- `weight`：正整数，默认 1；
- `priority`：整数，默认 100，用于稳定排序与恢复探测顺序；
- `schedule_current_weight`：平滑加权轮询的持久化当前权重；
- `consecutive_failures`：连续失败次数；
- `circuit_open_until`：熔断截止时间，可为空；
- `last_success_at`、`last_failure_at`：最近调用结果时间；
- `last_error`：截断、脱敏后的故障摘要；
- 创建与更新时间。

有效服务为：已启用、URL/密钥/模型完整，且 `circuit_open_until` 为空或已到期的服务。到期但尚未被探测的服务记为“待恢复”，依然只能以候选队列中的一次尝试恢复。

### `ImagingProviderAttempt`

每一次任务内的 provider 调用记录。

- `job`：关联 `ImageGenerationJob`；
- `provider`：关联 `ImagingProvider`；
- `attempt_number`：任务内递增序号；
- `status`：成功或失败；
- `started_at`、`completed_at`、`duration_ms`；
- `error`：脱敏、截断错误摘要。

### `ImageGenerationJob` 扩展

新增可空 `provider` 外键，成功时记录最终服务；任务最终失败时记录最后尝试服务（若存在）。任务尝试明细由 `ImagingProviderAttempt` 查询获得。

## 4. 后台 API 与界面

现有 `/api/admin/imaging/settings` 保持兼容，改为返回服务池摘要与旧配置迁移状态；新增面向主管理员的服务池 API：

- `GET /api/admin/imaging/providers`：服务列表与掩码密钥、健康摘要；
- `POST /api/admin/imaging/providers/create`：新增服务；
- `PATCH /api/admin/imaging/providers/<id>`：编辑服务、启停、更新密钥；
- `DELETE /api/admin/imaging/providers/<id>`：删除服务；
- `POST /api/admin/imaging/providers/<id>/test`：通过 `/models` 检查鉴权与模型可见性，不生成图片、不影响用户积分/任务或运行时熔断状态；
- `POST /api/admin/imaging/providers/<id>/recover`：清空失败计数、解除熔断，使其回到待调度状态。

`/admin/imaging` 页面显示服务池表格与新增/编辑表单：名称、启用、URL、模型、超时、权重、优先级、API Key（仅输入/掩码显示）、健康状态、失败次数、熔断倒计时、最近成功/失败、最近错误，以及测试、恢复、编辑、启停、删除操作。

所有相关 API 延续当前主管理员认证。绝不返回密钥明文、请求 `Authorization` 头或包含密钥的错误文本。

## 5. 服务选择与请求流程

### 5.1 候选选择

1. 在事务中锁定当前可调度服务；
2. 过滤掉禁用、配置不完整和仍处于熔断期的服务；
3. 先按 `priority`，再按主键确定稳定基线；
4. 用平滑加权轮询更新候选服务 `schedule_current_weight`：每个服务增加自身权重，选择当前权重最大者，再从选中服务扣减总权重；
5. 将首选服务放在第一位，其余服务按同一轮调度的确定顺序作为故障切换候选；
6. 无候选时直接生成失败，走既有退款闭环。

权重如 `5:3:1` 时，长期分配比例接近 5:3:1，且不会机械地连续把全部请求给某一个节点。

### 5.2 调用和切换

1. 任务进入 `generating`；
2. 依次调用候选服务；每次调用先创建 `ImagingProviderAttempt`；
3. 调用成功：记录尝试成功、清零该服务连续失败、清除错误与熔断、设置最近成功时间，并将任务图片与最终 provider 写入；
4. 调用失败：记录尝试失败、更新失败计数、最近失败和脱敏错误；若失败次数达到 3，设置 `circuit_open_until = now + 5 minutes`；随后立刻尝试下一候选服务；
5. 所有候选均失败：任务失败，错误为通用的“所有已启用显影服务暂时不可用”，并执行已有积分退款逻辑。

一次成功会将对应 provider 的连续失败计数清零。未被本任务尝试的服务健康状态不改变。

### 5.3 熔断恢复

- 熔断期内服务不会进入候选集；
- 到期服务重新进入候选集合并接受一次真实调用作为恢复探测；
- 该次成功即恢复健康；失败即依据新的失败计数重新熔断 5 分钟；
- 管理员可以通过“恢复服务”立即重置熔断与连续失败次数。

## 6. 兼容与迁移

保留现有 `imaging.cpa.base_url`、`imaging.cpa.api_key`、`imaging.cpa.model`、`imaging.cpa.timeout_seconds` 设置作为历史兼容来源。

迁移后首次读取/管理服务池时：若 `ImagingProvider` 尚为空但旧设置存在，创建名为“默认 CPA 服务”的服务，继承旧值、启用、权重 1、优先级 100。迁移应当幂等，避免多次创建。

完成迁移后，生成请求一律通过 `ImagingProvider` 读取配置。旧设置接口仍可读取和写入兼容的默认服务，避免现有后台调用立即失效；新界面以服务池 API 为准。

## 7. 错误与安全约束

- 每个错误摘要限制长度，并移除 API Key、Authorization 值及 URL 中敏感查询参数；
- 前端不显示底层响应正文中的敏感内容；
- provider URL、模型、超时、权重和优先级执行严格校验；
- OpenAI-compatible 裸域名自动规范化到 `/v1`，管理 API 同时返回最终模型列表和生图 Endpoint；
- 删除有历史尝试记录的服务时，尝试记录保留（provider 外键使用 `SET_NULL`，并保留 provider 名称快照）；
- 服务池并发选择及健康状态更新使用数据库事务与行锁，避免竞争条件。

## 8. 验证

自动化测试覆盖：

1. 主管理员可新增、编辑、启停、删除、测试、恢复多个服务；非主管理员被拒绝；
2. 密钥永不出现在读取响应中，只显示掩码与配置状态；
3. `5:3:1` 的平滑加权轮询具有预期长期比例；
4. 单次任务的服务失败立即切到下一个候选；
5. 连续 3 次失败后熔断 5 分钟，熔断期内不会被分配；
6. 熔断到期后成功恢复、失败重新熔断；
7. 全部服务不可用时任务失败并只退款一次；
8. 成功与失败尝试完整记录到 `ImagingProviderAttempt`；
9. 旧单服务设置自动创建默认服务且仍能完成生成；
10. 现有用户隔离、下载、幂等、图片落盘与积分测试持续通过。
