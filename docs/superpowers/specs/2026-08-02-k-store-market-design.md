# K 士多与 K 股市设计

- 日期：2026-08-02
- 状态：待用户评审
- 范围：数字兑换码商城、K 积分股市小游戏、有限资金机器人做市

## 1. 背景与目标

当前 KFlow 已有事务化积分账户与追加式积分流水，积分主要用于显影和下载兑换。本次扩展建立两个消费场景：

1. K 士多：管理员维护数字商品和兑换码库存，用户使用 K 积分兑换兑换码。
2. K 股市：用户直接使用 K 积分参与虚拟股票轮次，机器人提供有限流动性。

核心不变量：K 积分不能通过商城或股市被无限生成。每次余额变化都必须经过幂等积分流水；股市正向结算只能来自有限的机器人资金、用户投入或明确的管理员资金注入。

## 2. 设计决策

### 2.1 Django 应用边界

新增两个独立应用：

- `apps/store`：商品、兑换码、兑换记录和商城接口；
- `apps/market`：轮次、虚拟资产、报价、订单、持仓、机器人资金和交易审计。

两个应用复用 `apps.points.services.apply_ledger`，不直接修改 `PointAccount.balance`。积分规则仍由 `SystemSetting` 管理，新增商城和股市专属配置也使用带命名空间的设置键。

### 2.2 K 士多

商品字段包括名称、slug、说明、封面、K 积分价格、上下架状态、每人兑换上限和创建审计信息。兑换码以密文保存，使用部署固定的 Django 密钥派生加密密钥；后台列表不回显明文兑换码，只有成功兑换的用户可以查看自己的码。

兑换流程全部处于一个数据库事务：

1. 校验商品处于可兑换状态、用户未超过限额；
2. `select_for_update` 锁定商品和一条可用兑换码；
3. 用幂等键执行 `store_redeem` 负积分流水；
4. 创建兑换记录并将兑换码标记为已使用；
5. 返回兑换结果和当前余额。

任一步失败都回滚。兑换码被展示后不自动退回库存，管理员只能通过带原因的撤销/补偿流程处理异常。

建议模型：

- `StoreProduct`：商品及价格、限额、状态；
- `StoreCode`：商品、加密码文、摘要、库存状态、导入审计；
- `StoreRedemption`：用户、商品、兑换码、积分流水、幂等键、状态和时间。

### 2.3 K 股市与机器人

K 股市采用轮次制。每个轮次有开放时间、结算时间、手续费、限额、行情种子、机器人预算和待兑付额度。虚拟资产的报价由服务器根据轮次种子和时间片生成，客户端只能读取报价。

机器人是有限资金做市方：

- 有固定 K 积分现金预算和每个资产的固定库存；
- 使用固定价差报价，用户买入走 ask，用户卖出走 bid；
- 用户买入时扣除 K 积分，资金进入该轮次机器人资金池；
- 用户卖出时只有在资金池、机器人每日支付额度和用户持仓均满足条件时才支付；
- 买入前先锁定该持仓的最大可能结算额，资金池不足时拒绝新买入；轮次结束时按最终报价强制结算并释放锁定额度；
- 资金或库存不足时停止对应报价，不通过代码自动补充；
- 机器人资金注入必须由主管理员显式操作并写入资金审计流水。

所有用户买卖、手续费、机器人资金变化和结算都保留交易记录。机器人不会调用普通奖励逻辑，不会把盈利直接写成无来源的 `total_earned`。

建议模型：

- `MarketRound`：轮次状态、时间、手续费、限额、行情种子、机器人预算和待兑付额度；
- `MarketAsset`：虚拟股票名称、代码、基础价格和状态；
- `MarketQuote`：服务器生成的时间片报价；
- `MarketPosition`：用户在轮次中的持仓、成本和已实现盈亏；
- `MarketOrder`：买卖方向、数量、成交价、手续费、积分流水、幂等键；
- `MarketBotInventory`：机器人现金、资产库存、支付上限和余额；
- `MarketTreasuryLedger`：机器人资金注入、成交收入、成交支出和手续费审计。

### 2.4 防刷与限额

默认提供并允许主管理员调整：

- 单用户每日投入上限；
- 单笔订单上限；
- 单用户每日订单次数上限；
- 单轮最大持仓和最大收益；
- 机器人单轮最大亏损和每日最大支付额度；
- 买卖冷却时间；
- 市场全局暂停开关。

禁止杠杆、做空、借贷、用户间转账、提现和现金兑换。账户被冻结时不能提交商城兑换或股市订单。限额判断、资金扣除和持仓变化必须在同一事务中完成。

## 3. HTTP 与页面

### 3.1 用户端

- `GET /store`：K 士多页面；
- `GET /api/store/products`：可兑换商品和库存摘要；
- `GET /api/store/redemptions`：当前用户兑换记录；
- `POST /api/store/redeem`：使用幂等键兑换商品；
- `GET /market`：K 股市页面；
- `GET /api/market/round`：当前轮次和规则；
- `GET /api/market/quotes`：当前服务器报价；
- `GET /api/market/portfolio`：当前用户持仓和余额；
- `GET /api/market/orders`：当前用户交易记录；
- `POST /api/market/orders`：买入或卖出订单。

主页、个人中心和积分页面增加 K 士多、K 股市入口；未登录用户只能查看介绍，实际兑换和交易必须登录。

### 3.2 管理端

在现有主管理员后台增加：

- K 士多商品 CRUD、批量导入兑换码、库存和兑换记录；
- K 股市轮次创建/暂停/结算、虚拟资产管理、限额配置；
- 机器人预算、库存和资金注入；
- 股市订单、积分流水和异常审计。

所有写操作要求主管理员权限并记录操作人、原因和时间；API 不回传兑换码密文或其他用户的敏感数据。

## 4. 错误处理与一致性

- 重复幂等键返回原兑换/订单结果，不重复扣分；
- 库存耗尽返回明确的 `409`，不扣积分；
- K 积分不足、机器人资金不足、报价过期和限额超出均整体回滚；
- 股市暂停时拒绝新订单，但允许管理员执行结算或补偿；
- 管理员撤销兑换码或补充资金必须使用新的审计流水，不能修改历史流水；
- 所有用户余额读取使用现有积分账户服务，避免出现旁路余额。

## 5. 验证方案

测试覆盖：

1. 商城商品上下架、兑换码导入、并发兑换、幂等重试、余额不足回滚和用户隔离；
2. 股市报价读取、买卖成交、持仓更新、机器人现金/库存耗尽、限额、暂停、幂等和冻结账户；
3. 积分流水只追加、交易与余额一致、机器人预算不会自动增加；
4. 管理员权限、兑换码不泄露、接口未登录拒绝；
5. Django migration/check、全量测试、静态脚本语法和 HTTP 冒烟。

完成标准是：任何商城或股市成功路径都有对应积分流水和业务审计记录；在并发和重复请求下不能重复发码、重复扣分或超出机器人预算。
