# 显影缓存、图片压缩与静态资源加速设计

日期：2026-09-04

## 目标

在不改变现有显影接口兼容性、用户指定输出格式与原始像素尺寸的前提下，降低重复生成的外部服务开销，缩小生成图片体积，并提高图片与静态资源的重复加载速度。

## 1. 显影结果缓存

缓存键由当前用户、规范化后的完整提示词、图片尺寸、质量和输出格式计算 SHA-256。缓存仅在同一用户范围内共享，有效期为 30 天。

创建任务时先检查用户与幂等键；随后查找 30 天内参数一致、状态已完成且文件仍存在的任务。命中后仍按完整规则扣除积分，创建一条新的已完成任务记录并引用原图片文件，不进入 Worker、不调用外部显影服务。幂等重试继续返回已有任务且不重复扣分。文件缺失、缓存过期或跨用户请求均按普通生成处理。

响应新增 `cache_hit` 与 `cache_source_id` 字段，不删除或更改现有字段。

## 2. 图片压缩

外部服务返回内容后、保存前使用 Pillow 解码并验证图片。保持用户指定格式与像素尺寸，移除非必要元数据：

- PNG：无损优化。
- JPEG：质量 85、优化、渐进式编码，并转换到兼容色彩模式。
- WebP：质量 82、启用较高压缩方法。

仅当重新编码后的内容更小时使用压缩结果，否则保存原始内容。无效图片将使任务失败并触发现有退款流程。任务记录保存压缩前与最终字节数，便于后续观测。

## 3. 图片 HTTP 缓存

预览与下载响应使用图片 SHA-256 作为强 ETag，并提供 Last-Modified。支持 `If-None-Match` 与 `If-Modified-Since` 条件请求，匹配时返回 304。

图片属于登录用户，因此使用 `Cache-Control: private, max-age=86400`，不允许共享代理公共缓存。下载接口继续使用 attachment，预览接口继续使用 inline。

## 4. 静态资源加载优化

生产静态文件采用 Django Manifest 静态存储，`collectstatic` 生成带内容哈希的文件名。显影模板移除手写查询版本号并依赖静态文件版本机制。启用 GZip 中间件压缩 HTML、CSS、JS、JSON 和 SVG 等文本响应。

带哈希静态资源可由生产 Web Server 或 CDN 使用 `public, max-age=31536000, immutable`。开发服务器保持可直接运行。项目文档说明生产环境应从 `.staticfiles/` 提供资源及相应缓存头。

## 5. 数据模型

`ImageGenerationJob` 新增：

- `cache_key`：规范化参数哈希。
- `cache_hit`：是否直接复用结果。
- `cache_source`：可空自引用，指向原始结果任务。
- `original_bytes`：压缩前字节数。
- `stored_bytes`：最终存储字节数。

增加面向用户、缓存键、状态与完成时间的查询索引。缓存记录共享文件路径，因此删除或清理任务时必须先确认没有其他任务引用该文件；本次不新增自动删除历史图片的行为。

## 6. 错误处理与并发

积分扣除和新任务记录创建保持在数据库事务中。并发相同参数请求允许在首次结果尚未完成时各自生成；只复用已经完成的可靠结果，避免等待与任务依赖复杂度。缓存文件存在性检查失败时静默绕过缓存，不影响正常生成。

图片解码或压缩异常按生成失败处理，使用现有自动退款与用户可读错误机制；底层异常细节不暴露给客户端。

## 7. 测试与验收

测试覆盖：

- 30 天内命中、过期不命中、文件缺失绕过、跨用户隔离。
- 缓存命中仍完整扣分，幂等重试不重复扣分。
- PNG/JPEG/WebP 压缩、格式和尺寸保持、无效图片拒绝、最终内容不增大。
- ETag、Last-Modified、304、private Cache-Control。
- Manifest 静态配置、模板静态 URL 与 GZip 配置。
- Django `check`、迁移检查及全量测试。

实现完成后提交到当前 `master`，并推送到 `origin/master`。
